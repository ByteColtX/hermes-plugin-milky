## Context

见 `proposal.md` 的 Why。当前 `MuteTracker.initialize()` 已完成登录身份和群列表读取，
随后在一个异步初始化阶段逐群等待 `get_group_member_info(no_cache=true)`；适配器在该阶段
结束前不会启动 SSE 或开放普通消息入口。现有 `refresh_group()` 是运行期的单群维护路径，
已经具有每群锁、冷却和全局并发槽。本 change 只调整冷启动全量扫描，不改变运行期刷新边界。

## Goals / Non-Goals

**Goals:**

- 在群成员查询阶段一次性创建全部选中群的查询任务，让 200+ 群的初始化耗时主要由最慢
  的单个查询决定，而不是群数乘以单请求延迟。
- 保留每个查询的群 ID、Bot `self_id`、`no_cache=true` 和独立结果归属。
- 等待全部任务完成后再提交成功快照、完成初始同步并由 adapter 启动 SSE；任何失败仍使
  初始同步保持 fail-closed。
- 在初始化被取消或 client 关闭时回收全部未完成任务，并保留安全的扫描汇总观测。

**Non-Goals:**

- 不给初始扫描增加应用层 semaphore、worker 数、批次大小、排队窗口或自动降速；无界并发
  是本 change 的明确产品决策。
- 不改变运行期 `refresh_group()` 的每群锁、冷却、全局并发上限或发送失败后的刷新策略。
- 不绕过 `no_cache=true`，不跳过失败群，不在部分扫描完成时开放消息入口，不修改 Milky
  协议和 Hermes Gateway 的连接超时配置。

## Decisions

### 1. 初始成员查询使用一次性无界 fan-out

在登录和群列表成功后先确定最终选中群集合，再为每个群创建一个成员查询协程，并使用
一次聚合等待收集所有结果。任务数量与选中群数量相同，不在插件内设置并发闸门。这样直接
匹配已确认的 200+ 群启动场景，也避免以“提高 Gateway 超时”掩盖串行算法的规模问题。

备选方案是固定数量 worker 或 semaphore；它对服务端更保守，但用户已明确要求不采用有界
并发，且实测 242 个只读查询两轮均全部成功、约 2.6–3.0 秒完成。HTTPX 连接池的内部
行为仍由依赖自身管理，本 change 不把其实现细节当成插件容量保证。

### 2. 先收集结果，再在初始化阶段统一更新状态

每个任务只负责调用 Action、校验结果并返回“成功/失败及成员信息”的安全结果。初始化协程
在聚合完成后按原群集合处理结果、更新快照和统计值，避免多个任务同时改写同一份快照映射。
成功响应继续使用现有 `shut_up_end_time` 规则；失败群保留初始 `muted` 快照并计入失败数。

这不会改变 Gate 语义：聚合等待和所有必要结果处理结束前 `_initialized` 仍为 false，
adapter 仍不会进入 ready 状态。

### 3. 取消传播与任务清理优先于结果汇总

若初始化收到 `CancelledError`，必须取消尚未完成的成员查询并等待其退出，再向上重新抛出
取消；不能把取消误记为普通群查询失败，也不能遗留会继续使用 client 的后台任务。普通
单群异常仍转换为安全失败结果，由初始化按既有规则抛出 `MuteSyncError`。

### 4. 观测保持汇总而不记录敏感请求内容

保留现有 `scope`、`total`、`succeeded`、`failed`、`muted`、`unmuted`、`unknown` 汇总，
并增加可验证的初始化耗时或等价阶段观测（如实现选择记录）。日志不得包含 token、完整
URL、请求/响应正文或异常正文；群 ID 仅在既有确认的禁言群安全日志规则允许时记录。

## Risks / Trade-offs

- [一次性并发大量请求可能增加 Milky 服务端瞬时负载或触发连接池排队/限流] -> 这是已确认
  的策略取舍；通过 200+ 规模 fake/真实只读证据、失败分类和延迟观测验证，不把成功压测
  当作服务容量承诺。若真实部署出现服务端限流，应由后续独立 change 重新讨论策略。
- [一个失败会使整轮初始化失败] -> 保留现有 fail-closed 契约，失败群不被解释为 unmuted，
  Gateway 重连 watcher 负责后续连接重试。
- [Gateway 在初始化期间取消连接] -> 取消传播到所有成员任务并清理资源；adapter 继续保持
  未连接，不能启动半完成的 SSE 或消息入口。
- [完成顺序与群列表顺序不同] -> 结果必须携带原群标识，状态更新按群标识归属，不依赖任务
  完成顺序；扫描汇总仍以最终选中集合为准。

## Migration Plan

无需数据迁移或新增配置。部署实现后，启动连接自动使用新的初始扫描策略；已有稳态刷新和
重连状态语义保持不变。回滚只需恢复旧实现，但在恢复串行逻辑后 200+ 群仍可能重新触发
Gateway 30 秒连接超时。

归档前必须完成聚焦测试、200+ 群规模测试、取消/失败清理测试及项目质量门禁；真实 Milky
压测结果仅作为本 change 的外部证据，不写入凭证、真实群号或完整响应。
